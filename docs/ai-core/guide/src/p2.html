Chapter 1

Introduction

SmartBuildOS AI Core is a Control4 driver plus a cloud AI layer for professional Control4 dealers. The driver turns Composer programming into validated requests to the SmartBuildOS cloud and turns the cloud's results back into Composer events and variables. All AI runs in the cloud; the controller holds no AI, no history beyond a small buffer, and no AI provider key.

How to read this guide. It documents what was built and verified on the AI Core branches as of 18 November 2026 (driver branch feat/ai-core; platform branch codex/ai-core at commit dbdd9b67c), and nothing else. Nothing in it has been released: the branches are pushed and their pull requests are open but not merged, nothing is in the Driver Store, and no migration is applied to production or to any remote database. Every name in it is copied from the driver's driver.xml, the protocol specification or the platform source. Coloured callouts say what is simulated, in development, or blocked. The Verification status page lists every one of them.

What it does

  • Asks and explains. Composer programming can ask a question (AI_ASK), request an analysis of a room or the whole system, a scene suggestion, a report or a diagnostic. The answer arrives later as the AI Response Ready event and the AI_LAST_RESPONSE variable. It can also run the household analysis (AI_RUN_HOUSEHOLD_ANALYSIS, Run Household Analysis), whose findings appear in System Studio, not on the controller.
  • Reads history instead of guessing. In the cloud, the AI may only answer historical questions from : stored Flight Recorder event ids returned by a tool in the same turn. Confirmed causes are kept apart from possible ones; unknown stays unknown.
  • Records what programming reports. AI_RECORD_EVENT lets a dealer drop a named marker into programming, because Control4 gives a driver no way to see programming run.
  • Learns, when switched on. Learning is off by default and is switched on per property in System Studio; the homeowner can pause it, exclude rooms and kinds of activity, correct, export and erase. Deterministic detectors find routines and preferences with sample-size confidence.
  • Proposes, never decides. The model only emits typed tool calls; a deterministic permission engine authorizes each one. Device actions are proposals that a person approves; they run through the existing SmartBuildOS command queue, not through this driver.
  • Reports its health. Read-only Composer properties show the Agent link, licence, provider status, telemetry and learning state.
  • Has its own touchscreen tile. A Navigator tile shows the AI Core status to anyone; the chat opens only after an owner PIN from PIN Lock and locks again after five minutes, and an owner PIN can approve one low- or medium-risk request at a time when the homeowner allows it (Chapter 8).
  • Hears from every other SmartBuildOS driver. Each driver shows an AI Core property saying whether it found AI Core; root drivers report what they are, their state, events and faults; AI Core can ask a driver a read-only question it declared, and a driver can declare an action that a person must always approve (Chapter 6).

Architecture overview

AI Core has three layers. On the controller, the AI Core driver talks only to the SmartBuildOS Agent, hub-and-spoke, using module contract v2. The Agent relays a closed list of to one fixed platform route. In the cloud, the platform authorizes, runs the AI provider, reads Flight Recorder history and keeps learning data. People see and approve things in the interfaces: System Studio for staff and the homeowner portal. Select any component to see what it does and what it connects to.

Important limitations

  • No hardware run. No physical controller has run the driver, the Flight Recorder's v2 service, or module contract v2. The bench list is in Developer Reference.
  • No live AI call. Every provider test uses mocked HTTP built from vendor documentation; no request has gone to Anthropic or OpenAI with a real key.
  • Control4 does not tell a driver who caused a change, what the value was before, or that a programming item ran. AI Core never claims any of these; such links are labelled possible.
  • The driver never controls equipment. Its only proxy is its own touchscreen tile (a uibutton), which addresses no device; actions go through the Agent's command queue after approval.
  • Persistent programming is never written. DriverWorks has no write API for programming; a change becomes a recommendation a person carries into Composer.
  • Local pub/sub is lossy by design. The Agent's durable cloud queue is the record.
  • Platform cloud results depend on a route that is not deployed. Until /api/integrations/control4/modules/rpc is deployed, the Agent gets 404 and the driver sees cloud_refused.
  • No real booking, calendar or Places call. The concierge's only working provider is a labelled SIMULATION sandbox; nothing is booked at a real restaurant. See Chapter 9.
  • Learning is off by default. A controller collects nothing for learning until System Studio switches learning on (Chapter 7).

Obtaining the C4Z

The file is smartbuildos-ai-core.c4z. No GitHub release and no store package of AI Core has been published (both are owner actions, RELEASE.md), and there is no current local build either: the only one predates the touchscreen page and driver reporting (checklist 10.8, Blocked: no packager in this worktree).

  • Local build: make build in the driver repo writes it to dist/oss/ and copies it into ~/Documents/Control4/Drivers. make build stamps <version> with the UTC time (YYYYMMDD.HHMMSS) and its formatter rewrites tracked files, so build on a clean checkout or a scratch copy. The only build recorded in the checklist is version 20261118.091052 (92,634 bytes), which predates the touchscreen page and driver reporting; no build has been made since (10.8 is Blocked).
  • Later, a release: download it from the release's assets.
  • Updates after the first install come through the Agent's updater (the SmartBuildOS store or GitHub, the Agent's Update Source), which only updates drivers already in the project; it never adds AI Core by itself, and it never downgrades (a rollback is a manual reinstall).

Use the Agent, the Flight Recorder and AI Core from the same build.

Adding the driver in Composer

The order is Agent → Flight Recorder → AI Core:

  1. Copy smartbuildos-ai-core.c4z (and smartbuildos-flight-recorder.c4z) into the Composer drivers folder (Documents/Control4/Drivers).
  2. Make sure the Agent is installed (Agents panel) and paired: its Connection Status should read connected and its pairing shown.
  3. Optional: add SmartBuildOS Flight Recorder to any room.
  4. Items → Search → SmartBuildOS AI Core → add it to a room. Its AI Core tile appears in that room's Navigator (move or hide it like any tile). One per project: a second instance is refused by the Agent's singleton rule.
  5. For the touchscreen chat and approvals, add SmartBuildOS PIN Lock too (next section).

The AI Core tile and PIN Lock

The tile has not been opened on a real touchscreen or phone yet (KNOWN-ISSUES.md KI-53 to KI-60). These steps are INSTALLATION.md §10.

  1. Check the address. Webview Address reads http://<controller>:47871/app (home network only). If it reads Controller address unknown: set App Relay Address, set App Relay Address to the controller's LAN address, and the same value on PIN Lock; then run the action Republish App URL and close and reopen the tile (Navigator does not change the address of an open page).
  2. Add PIN Lock. Install SmartBuildOS PIN Lock in the same project, licence it, and create an owner code with a PIN on PIN Lock's own page. Leave its AI Core PIN Verification property on. Only owner PINs work on the AI Core tile; staff, vendor and guest codes never do. Wrong PINs count against PIN Lock's own lockout (Clear Lockouts on PIN Lock clears it).
  3. The homeowner's two switches are in the SmartBuildOS portal and are off until the homeowner turns them on: nothing in Composer turns them on (Chapter 8). Touchscreen Detail can only lower what the homeowner allowed: Basic switches the chat off, Standard never asks for household activity, Household asks for it but the cloud answers with it only when the homeowner's switch is on.
  4. Home network only. A touchscreen or a phone on the home Wi-Fi reaches the page; a phone away from home does not (the page says so). There is no cloud fallback.
  5. Check it. Open the tile: the status shows Online and that PIN Lock is ready for this screen. Touchscreen Approvals says in plain words what is missing when it is not.

Controller selection

Add AI Core to the controller that runs the SmartBuildOS Agent: the driver finds the Agent on the same project (no smartbuildos.c4z found means no_agent), and the module registry, pub/sub and requests all run inside that Agent. Only one AI Core can be live per controller.

Connections

AI Core declares one proxy and one connection, both for its touchscreen tile: a primary uibutton proxy on binding 5001 (connection 5001, UIBUTTON), with a web view (controller://driver/smartbuildos-ai-core/app/index.html, also enabled in the phone app) — the way PIN Lock and Atmosphere build their tiles (Chapter 8). There is nothing to bind: the tile appears in the room the driver was added to. The proxy addresses no equipment. AI Core reaches the Agent with C4:SendToDevice, and the Agent reaches the cloud. Tests record every C4:SendToDevice the driver makes and show that all go to the Agent and that SetDeviceVariable, SendToProxy, SendUIRequest, RegisterDeviceEvent and Bind are never called.

Pairing with the SmartBuildOS Agent

AI Core does not pair itself: the Agent is paired (Pairing Code or the account-number flow on the Agent), and AI Core follows it. Pair the Agent before or after adding AI Core — both work: AI Core re-reads the Agent's state on every registration and on the Agent's state updates, with no reload. An Agent from this branch also registers for Director system events at the moment it is paired. At LateInit the driver sends SBOS_MODULE_REGISTER with its v2 ; the Agent answers SBOS_MODULE_REGISTERED with a per-registration token and forwards the last SBOS_DRIVER_CONFIG for SBOS_AI_CORE. Registration retries every 30 s, doubling to 5 min.

  1. Test Agent Link (Actions). Last Test Result should read Agent link: OK at <time> — Agent <version>, protocol 1..2, paired, cloud connected; N module(s). registered at protocol 1; this driver needs an Agent update (protocol 2) means the Agent is too old.

    AI Provider Setup

    AI Core uses the customer's own Anthropic (Claude) or OpenAI account. Provider setup happens in System Studio, on the property's Intelligence page, tab Provider & settings.     How the provider layer works

    One neutral interface sits over both vendors (src/lib/ai-core/providers/): Anthropic through the Messages API and OpenAI through the Responses API with store:false. Call sites ask for a model class, deep or fast, never a model id. Keys are passed per call and never stored by the library; it reads no environment variable for keys. toolChoice is auto or none only, and no temperature is sent.

    Secure key entry

    Keys are entered only in System Studio, never in Composer. The Composer property AI API Credential is read-only status. The driver never receives, stores or displays a key, and refuses a whole configuration document if any key in it is credential-shaped (api_key, token, secret, …) or a display string looks like a key (sk-…, Bearer …, long opaque blobs).

    Connectivity test

    POST /api/monitoring/ai-core/credentials/test with { property_id, provider } (monitoring:manage) tests the key the property's calls would use with a token-free call, GET /v1/models on either vendor. It answers ok or the error kind (auth, permission, network, …), never the vendor's message, which can echo the key. Tests are limited to 6 per minute per property (connectivity_test_limit: "Too many connection tests. Wait a minute and try again."). Whether either vendor bills GET /v1/models could not be verified from their documentation.

    In Studio the Test connection button runs this test; too many tests answer Too many connection tests just now. Wait a minute and try again.     SmartBuildOS Agent Integration

    The SmartBuildOS Agent (smartbuildos.c4z) is AI Core's only peer on the controller. It authenticates AI Core, routes its messages, relays its cloud ops, forwards its configuration, licenses it and carries its events to the cloud.

    What the Agent does for AI Core

    • Registry and tokens. Registers AI Core as ai_core and issues a per-registration token minted from C4:UUID("RANDOM") when Director returns one (otherwise the v1 generator).
    • Sender stamping. Writes from_module_id / from_instance_id itself; a module's own claim is never forwarded.
    • Cloud relay. POSTs AI Core's cloud ops to /api/integrations/control4/modules/rpc with its pairing token. The platform derives tenant and property from that token only.
    • Configuration. Forwards SBOS_DRIVER_CONFIG for SKU SBOS_AI_CORE; AI Core answers SBOS_DRIVER_CONFIG_ACK.
    • Restricted operations. Delivers the platform's six closed operations as SBOS_MODULE_COMMAND.
    • Durable event path. Queues AI Core's envelopes and uploads them; acknowledges with SBOS_MODULE_EVENTS_ACK.
    • Licensing. Answers the licence SDK (sbos.license) for SKU SBOS_AI_CORE.

    Registration and liveness

    LateInit registers with the v2 manifest (driver sbos.ai_core; AI Core serves no capability to other modules). On SBOS_MODULE_AGENT_HELLO it re-registers (new token) and re-subscribes; on SBOS_MODULE_DIRECTORY_CHANGED it re-reads the directory 2 s later.     3. The first document of at least that version decides learning, whatever the preview said.
    4. Switching learning on is refused while the last document was refused; switching it off is always accepted.

    • Normal path: module client stage (≤ 300, frames of ≤ 100, 30 s ack, 3 tries) → the Agent's durable acknowledged queue → the cloud.

    Licence behaviour

    The Agent is the licensing authority for SKU SBOS_AI_CORE (sbos.license). On the controller, commands, run_diagnostic and collection stop only when license.enforces() — a definitive denial with enforcement on. Grace, trial, legacy, cloud-validation-required and no-answer states fail open. Features gated on the controller: BASE (every command, run_diagnostic, Test AI Connection) and AI_LEARNING (AI_LEARN_PREFERENCE, set_learning on, learning.active).     • No driver-side transfer workflow: transferring a licence is a platform staff action; the old controller then sees NOT_ENTITLED.
    • The platform never issues CONTROLLER_MISMATCH for SBOS_AI_CORE (only for System Link); the Agent does not compare an assertion's controller_id with its own identity — binding rests on the per-controller signing secret (KI-25).
    • An assertion that fails verification is dropped and the SKU answers LEGACY, which is operational: a forged assertion does not license AI Core, but it does not stop it either (KI-24; owner decision 11).

      Chapter 6

      Driver-to-Driver Integration

      DriverWorks gives drivers no sender identity, no broadcast and no delivery guarantee. Module contract v2 supplies them, hub-and-spoke through the SmartBuildOS Agent: discovery, local pub/sub, module-to-module requests, and a closed-vocabulary cloud relay. It is a strict superset of v1, so v1 modules keep working.

      The model

      Every frame is C4:SendToDevice(id, COMMAND, params) into the receiver's ExecuteCommand. Params are strings; structured data is JSON in one param. Module → Agent frames carry the v1 auth triple (module_id, instance_id, token); the Agent ignores, without answering, any frame that fails authentication. Agent → module frames carry the recipient's triple, so another driver cannot inject answers. Negotiation: both sides support PROTOCOL_MIN = 1, PROTOCOL_MAX = 2; AI Core requires 2 and reports agent_update_required against a v1-only Agent.

      Capability discovery

      SBOS_MODULE_DISCOVER (optional filter {module_id?, capability?}) is answered by SBOS_MODULE_DIRECTORY: the Agent's state (version, protocol_min, protocol_max, paired, connected) and every registered module (module_id, instance_id, driver, driver_version, protocol, status, stale, capabilities[]). Modules not heard from for 15 minutes are stale. Tokens are never included. When a module registers, unregisters or goes stale, the Agent pushes SBOS_MODULE_DIRECTORY_CHANGED 5 s after the first change of a burst. Consumers discover; they never assume.

      Registration and the capability manifest

      SBOS_MODULE_REGISTER takes an optional manifest (JSON ≤ 2 KB, ≤ 24 capabilities). A malformed manifest does not fail registration; the reply carries manifest_error (invalid_manifest, manifest_too_large, too_many_capabilities, invalid_capability). A capability a driver cannot serve locally must not be advertised.

      Subscriptions

      SBOS_MODULE_SUBSCRIBE (subscription_id, topics: 1–16 ) is answered by SBOS_MODULE_SUBSCRIBED (ok, reason, granted, refused). The Agent fans out only envelopes it accepted, in SBOS_MODULE_PUBLISH frames (≤ 25 envelopes, 1 s after the first buffered one, with a dropped count). At most 8 subscriptions per instance. Subscriptions live in Agent memory and are re-sent after every registration.

      Request / response

      The requester sends SBOS_MODULE_REQUEST (request_id, idempotency_key, to, capability, args ≤ 16 KB, deadline ≤ now + 60 s). The Agent acknowledges with SBOS_MODULE_REQUEST_ACK (Routed or Refused with a code), forwards the request to the target with the stamped sender, and relays the target's SBOS_MODULE_RESPONSE (status, error_code, result ≤ 24 KB, optional cursor). Only the instance the request was routed to may answer. Retries use the same : the Agent replays a stored answer (replayed = "true") instead of routing it twice.

      Retry rules (client library): only deadline_exceeded, target_unavailable, rate_limited and cloud_unreachable are retried — at most 2 retries, after 2 s then 5 s, with the same key and a fresh request_id.

      Declared read-only queries and declared actions

      A driver may declare read-only queries (for example current conditions) and actions (for example Mode Composer's activate_mode). Declarations are data inside three fixed AI tools; a driver can never add, name or shape a tool.

      Asking a driver a question. In a conversation the AI may call drivers_run_query for a query the driver declared. The platform checks the parameters against the stored declaration and sends run_driver_query; AI Core passes it to that driver (10 s), and the answer comes back as driver_query_result. The tool waits up to 15 seconds and otherwise says honestly that the answer is pending.

      A driver's action, always approved by a person:

      1. The AI can only propose it with drivers_propose_action (risk medium), in a person's conversation. Nothing runs on the model's say-so, and no pre-approved rule can match it.
      2. The proposal is at least medium risk; every action of a driver that controls a lock or security equipment is high: only the homeowner can approve it, in the portal, never with a touchscreen PIN, never automatically.
      3. The homeowner approves it (in the portal, or at the touchscreen with an owner PIN for a medium action when they switched that on). The homeowner's Composer Remote Control level must be Comfort or above.
      4. The platform sends invoke_driver_action. The Agent refuses it below Comfort; AI Core sends it only to a driver the Agent verified, once, never retried, and the driver refuses it if its declaration changed since it was approved (the declaration hash).
      5. The real outcome comes back as driver_action_result: started, completed or failed. Started is never shown as completed; an action with no answer in 20 seconds is reported failed with an unknown outcome (KI-49).

      On a real controller none of this has run: Mode Composer's activate_mode running and reporting its outcome is blocked on hardware (checklist 12.18). Staff see every reporting driver on the Studio Connected drivers page.

      Chapter 7

      Household Learning

      AI Core learns routines and preferences from deterministic detectors with sample-size confidence; the language model phrases findings, it does not invent them. Learning is off by default and is switched on per property in System Studio. The homeowner sees everything learned in the portal — what they told us, what was inferred, and suggestions awaiting their yes — and can pause, exclude, correct, export and erase.

      Switching learning on

      • Off by default. learning_enabled defaults to false on the platform, and on the controller learning.active defaults to false: Learning Status reads Off (not switched on in System Studio), LEARNING_ACTIVE is false and nothing is collected (Chapter 4).
      • Switched on in System Studio, Intelligence › Provider & settings › Learning › Learning on (needs monitoring:manage; agree it with the homeowner first). The save republishes the document and sends set_learning to the controller at once.
      • The homeowner can pause and exclude, not switch learning on (portal PATCH /api/portal/ai-core/learning refuses nothing else; a pause reaches the controller at once and the cloud stops analysing at once).
      • Learned data in Studio and the portal's learned and recommendations areas also need the AI_LEARNING licence feature; today only an explicit licence row grants it (owner decision 7). The homeowner's review, correct, pause, export and erase controls never need the licence.

      How it learns

      The analyze_property job reads stored events, applies the homeowner's controls (pause, exclusions, erase watermark) before any detector, and runs 14 pure detectors:

      DetectorEvidence threshold
      scene_override, thermostat_override≥ 10 activations, rate ≥ 40 %
      daily_routine≥ 15 of the last 30 days, 60-minute local window
      weekly_routine≥ 4 weeks, ≥ 75 % of that weekday
      unused_scene90 observed days of scene recording, 0 activations (today always insufficient_context: no scene inventory exists)
      device_failure≥ 8 offline transitions within 7 days
      frequent_room≥ 50 events, ≥ 7 days, ≥ 15 % share
      lighting_level, shade_preference, media_volume, media_source≥ 10 samples, ≥ 5 days, modal share ≥ 40 %
      favourite_scene≥ 10 activations, ≥ 5 days, ≥ 20 % share
      automation_conflict≥ 10 change-and-revert within 120 s on ≥ 3 days (labelled possible)
      seasonal≥ 365 days of history (not built in v1; answers insufficient_history)

      Thresholds marked "AI Core v1" in the source (weekly routine, frequent room, preferences, favourite scene, automation conflict, seasonal) are this phase's choice and await architect/owner review. Analysis runs on demand (POST /api/monitoring/ai-core/patterns {action:"analyze"}), idempotent per property per 10 minutes.

      Running the household analysis: the dealer's schedule and the programming command

      Decided by the owner on 18 November 2026 and built on both branches (checklist 6.7, Tested: platform unit tests; the driver side rerun by the conductor on a snapshot; simulation only, the schedule columns are applied to no database). Every trigger goes through one entry point and one gate chain (patterns/entry.ts). The analysis makes no AI provider call, so usage budgets do not gate it; one analysis runs at a time per property.

      1. The dealer's schedule (System Studio). Intelligence › Provider & settings › Household analysis schedule: Runs — Off — only when started here or by the controller (the default), Daily or Weekly; At an hour, and On a weekday for weekly, in the property's local time. The platform checks hourly (/api/cron/ai-core-analysis), so it runs within that hour. The saved schedule's status shows the next run, the last analysis and the last scheduled run (or why it was skipped); a property without a time zone cannot run a schedule, and a slot missed by more than a few hours is not made up. It runs only while learning is on and not paused, with AI_LEARNING licensed.
      2. The programming command (Composer). AI_RUN_HOUSEHOLD_ANALYSIS, described as Run Household Analysis (op analyze_household), for example after the house goes to Sleep or from a dealer-only button. It needs AI_LEARNING; at most one accepted run an hour from the controller and one request waiting at a time (a refusal, a lost connection or a timeout does not use up the hour), and SmartBuildOS keeps its own limit of one accepted run an hour per home. The normal answer is accepted (queued); the driver is never told when the run finishes and AI Response Ready does not fire: the findings appear in System Studio. Refusals name their reason (learning_not_allowed, not_licensed, already_running, rate_limited with the wait). Whether Composer lists the command as expected is unchecked in a real Composer (KI-40).

      Confidence scores

      n = sample size, T = the detector's evidence threshold, c = consistency in [0,1]
n < T          → no finding (never rounded up)
confidence     = c × n / (n + T)       0.5·c at threshold, → c as n grows
band           = low (n < 2T) · medium (n < 4T) · high (n ≥ 4T)

      The band comes from sample size alone. For a fixed consistency the score strictly increases with the sample size.

      Preference memory

      Memories are structured rows with full-text search (no vector store in v1), in four categories: system, explicit_preference, behavioral, operational. Each is verified or inferred and records its source: homeowner_stated, staff_entered, detector, registry, programming or model_proposed. Statuses: active, corrected, superseded, deleted, pending. The AI reads active memories with the memory_search tool (household data; needs AI_LEARNING). Staff can add a verified fact (POST /api/monitoring/ai-core/memories), never an inference and never a person.

      From Composer: AI_LEARN_PREFERENCE

      AI_LEARN_PREFERENCE (STATEMENT ≤ 300 characters, optional ROOM) sends cloud op learn_preference. The driver refuses it locally while learning is off or paused, or when the licence (enforced) lacks AI_LEARNING. The platform records the statement as a verified explicit preference with source programming (shown to the homeowner as Your home's programming states it) and answers completed at once (job_id: null): no job is tracked and AI Response Ready is not fired. It refuses with not_permitted when learning is not enabled or is paused, the feature is missing or the room is excluded; with invalid_args for a statement that names a person; and with rate_limited beyond 100 programming memories per property.

      Pending proposals from a conversation

      In a person's conversation the AI may call memory_propose to propose one memory (never in a Composer job). A proposal is stored as pending, is not used for anything, and waits for the homeowner (portal) or authorized staff (Studio › Recommendations › Pending memories) to accept or reject it; accepting makes it active and verified, rejecting deletes it to a content-free tombstone. It never describes a person, and the property's learning controls apply first.

      What my home has learned (homeowner portal)

      In the client portal, Your home assistant › What my home has learned is the homeowner's privacy centre. The area appears only when the property is licensed with AI_LEARNING. It shows, from /api/portal/ai-core/memories and /learning:

      • Your controls: Learning is on / paused with Pause learning (and resume), Rooms not to learn from, Kinds of activity not to learn from (security is never learned from today, whatever is chosen), Download my data and Erase everything learned (behind a deliberate confirmation).
      • Suggestions waiting for your yes — The assistant suggested these. They are not used for anything until you accept them. Buttons Yes, that's right / No, reject it.
      • Things you told us — Stated by you, your integrator or your home's programming — not guesses. Buttons Change it / Delete.
      • Things we inferred — Guesses from how your home was used. Each shows how confident it is and why. They describe how devices were used, never who used them. Each shows its confidence, a Why do you think this? disclosure with the evidence counts, and That's not right — correct it / Delete.

      Behavioural analysis — what the data cannot support

      • Occupancy: device interactions are not occupancy. Room findings are interaction_based unless a motion/occupancy sensor was the source.
      • Who caused a change, and the value before: not recorded; override and conflict statements say so.
      • Security, locks, access: never learned from; no enable switch exists.
      • Away / vacation recommendations: not generated in v1.
      • Rarely used scenes: answers insufficient_context — there is no scene inventory, and it needs 90 observed days.
      • Seasonal patterns: need ≥ 365 days; answer insufficient_history.
      • No time zone: time-of-day detectors answer insufficient_context rather than use UTC.
      • Markers are not learning: the learning engine never learns from AI_RECORD_EVENT markers; it reads only observation.change.
      • Identity: no finding has a person field; inferred text is scanned for person-implying words. Residual limit: a room or device label an installer named after a person ("Emma's Room") passes through as the label.

      Correcting assumptions

      Behind the portal screen, /api/portal/ai-core/memories:

      • PATCH { property_id, memory_id, action: "correct", value, statement? } — a verified replacement; the old row becomes corrected (inferred) or superseded (verified).
      • PATCH { …, action: "accept" } — accept a pending suggestion.
      • PATCH { …, action: "assign_to_me" } — links the homeowner's own stated preference to their profile (the only way a profile is ever set).
      • DELETE ?property_id=&memory_id= — content erased; a content-free key stops the same inference being re-learned.

      Staff can dismiss a recommendation (PATCH /api/monitoring/ai-core/recommendations/[id] { to: "dismissed" }); the homeowner can dismiss one shared with them, or approve one whose approver includes the homeowner (PATCH /api/portal/ai-core/recommendations). A recommendation that needs both the homeowner and the integrator (homeowner_and_integrator; no detector produces one today: each sets the homeowner or the integrator, src/lib/ai-core/recommendations/generate.ts) records each party's approval and becomes approved only when both have; either party may dismiss it; Studio and the portal show whose approval is awaited. Nothing is executed by approving a recommendation.

      Privacy settings

      • Pause and exclusions: PATCH /api/portal/ai-core/learning { property_id, paused?, excluded_room_ids?, excluded_categories? } (categories from lighting, scenes, climate, shades, media, occupancy, keypad, device_health, security, other).
