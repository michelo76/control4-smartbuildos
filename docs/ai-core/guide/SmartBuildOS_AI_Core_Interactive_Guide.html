Chapter 1

Introduction

SmartBuildOS AI Core is a Control4 driver plus a cloud AI layer for professional Control4 dealers. The driver turns Composer programming into validated requests to the SmartBuildOS cloud and turns the cloud's results back into Composer events and variables. All AI runs in the cloud; the controller holds no AI, no history beyond a small buffer, and no AI provider key.

How to read this guide. It documents what was built and verified on the AI Core branches as of 18 November 2026, and nothing else. Every name in it is copied from the driver's driver.xml, the protocol specification or the platform source. Coloured callouts say what is simulated, in development, or blocked. The Verification status page lists every one of them.

What it does

  • Asks and explains. Composer programming can ask a question (AI_ASK), request an analysis of a room or the whole system, a scene suggestion, a report or a diagnostic. The answer arrives later as the AI Response Ready event and the AI_LAST_RESPONSE variable.
  • Reads history instead of guessing. In the cloud, the AI may only answer historical questions from : stored Flight Recorder event ids returned by a tool in the same turn. Confirmed causes are kept apart from possible ones; unknown stays unknown.
  • Records what programming reports. AI_RECORD_EVENT lets a dealer drop a named marker into programming, because Control4 gives a driver no way to see programming run.
  • Learns, when the homeowner allows it. Deterministic detectors find routines and preferences with sample-size confidence. Learning is off by default.
  • Proposes, never decides. The model only emits typed tool calls; a deterministic permission engine authorizes each one. Device actions are proposals that a person approves; they run through the existing SmartBuildOS command queue, not through this driver.
  • Reports its health. Read-only Composer properties show the Agent link, licence, provider status, telemetry and learning state.

Architecture overview

AI Core has three layers. On the controller, the AI Core driver talks only to the SmartBuildOS Agent, hub-and-spoke, using module contract v2. The Agent relays a closed list of to one fixed platform route. In the cloud, the platform authorizes, runs the AI provider, reads Flight Recorder history and keeps learning data. People see and approve things in the interfaces: System Studio for staff and the homeowner portal. Select any component to see what it does and what it connects to.

Important limitations

  • No hardware run. No physical controller has run the driver, the Flight Recorder's v2 service, or module contract v2. The bench list is in Developer Reference.
  • No live AI call. Every provider test uses mocked HTTP built from vendor documentation; no request has gone to Anthropic or OpenAI with a real key.
  • Control4 does not tell a driver who caused a change, what the value was before, or that a programming item ran. AI Core never claims any of these; such links are labelled possible.
  • The driver never controls equipment. It has no proxies and no connections; actions go through the Agent's command queue after approval.
  • Persistent programming is never written. DriverWorks has no write API for programming; a change becomes a recommendation a person carries into Composer.
  • Local pub/sub is lossy by design. The Agent's durable cloud queue is the record.
  • Platform cloud results depend on a route that is not deployed. Until /api/integrations/control4/modules/rpc is deployed, the Agent gets 404 and the driver sees cloud_refused.
  • Concierge bookings are not available. See Chapter 9.

Chapter 2

Installation

Installing AI Core means: an Agent with contract v2 that is paired, the AI Core driver added once, the configuration delivered from System Studio, and a test of the Agent link and the provider.

Obtaining the C4Z

The driver file is smartbuildos-ai-core.c4z, built from drivers/smartbuildos-ai-core in the driver monorepo. Updates go through the Agent's existing store updater (Agent DRIVER_FILENAMES; store sku_for), like every SmartBuildOS driver.

A .c4z has been built from the AI Core worktree during the simulation runs, but packaging for release is still in progress (checklist 10.8) and store publication waits for the owner (10.12). The packaging test (test/test_aicore_package.lua) checks the module closure and a built .c4z when one is present. Installation and release procedures are in docs/ai-core/INSTALLATION.md and RELEASE.md in the driver repo.

Adding the driver in Composer

  1. Install and pair the SmartBuildOS Agent (a build with module contract v2).
  2. Optionally add the SmartBuildOS Flight Recorder.
  3. Add SmartBuildOS AI Core to the project, in any room. It appears under the Utility category (manufacturer SmartBuildOS, model AI Core).
  4. Wait for SmartBuildOS Connection Status to read Connected and AI Status to read Ready. Run Test Agent Link if it does not.
  5. In System Studio, choose the AI provider, enter its key, and set learning, exclusions and the permission mode. AI Provider, AI Model, AI API Credential and Permission Mode fill in when the configuration arrives.
  6. Run Test AI Connection.

Controller selection

Add AI Core to the controller that runs the SmartBuildOS Agent: the driver finds the Agent on the same project (no smartbuildos.c4z found means no_agent), and the module registry, pub/sub and requests all run inside that Agent. Only one AI Core can be live per controller; a second instance is refused while the first is not stale. The controller must run OS 3.3.2 or later.

Connections

AI Core declares no Composer connections, no proxies and no capabilities (the <connections>, <proxies> and <capabilities> elements of driver.xml are empty). There is nothing to bind. It reaches the Agent with C4:SendToDevice, and the Agent reaches the cloud. Tests record every C4:SendToDevice the driver makes and show that all go to the Agent and that SetDeviceVariable, SendToProxy, SendUIRequest, RegisterDeviceEvent and Bind are never called.

Pairing with the SmartBuildOS Agent

AI Core does not pair itself; it relies on the Agent's pairing. At LateInit the driver sends SBOS_MODULE_REGISTER with its v2 . The Agent answers SBOS_MODULE_REGISTERED with a per-registration token and the negotiated protocol, then forwards the last SBOS_DRIVER_CONFIG for SKU SBOS_AI_CORE. Registration retries every 30 s, doubling to 5 min. Agent Pairing Status shows Paired, Not paired, No SmartBuildOS Agent, Agent update required or Unknown (not registered with the Agent yet).

Verifying communication

  • Test Agent Link (TEST_AGENT_LINK) sends SBOS_MODULE_DISCOVER and writes the Agent's version, protocol range, pairing, cloud state and module count to Last Test Result, or why it cannot (no Agent, protocol 1, failed with a code).
  • Test AI Connection (TEST_AI_CONNECTION) calls the cloud op test_provider. Last Test Result says accepted (with a job id; the result arrives as AI Response Ready) or the refusal code.
  • Variable AGENT_CONNECTED and conditional AGENT_CONNECTED are true while the driver is registered and the Agent answers.

Initial synchronization

Sync Now (SYNC_NOW) re-registers if needed, drains the buffer, flushes staged events, re-reads the directory, sends a status frame and, on protocol 2, calls cloud op status with the applied config version. Last Synchronization records the last time the platform was heard: configuration applied, a restricted operation, an accepted cloud answer, or Sync Now. Until System Studio delivers configuration, Property ID and Controller ID read Not delivered yet (System Studio).

    Chapter 3

    AI Provider Setup

    AI Core uses the customer's own Anthropic (Claude) or OpenAI account. The key is entered in System Studio, encrypted in the AI Core vault, and never sent to the controller. Composer only ever shows a status line such as Configured in System Studio · Anthropic ••••abcd.

    How the provider layer works

    One neutral interface sits over both vendors (src/lib/ai-core/providers/): Anthropic through the Messages API and OpenAI through the Responses API with store:false. Call sites ask for a model class, deep or fast, never a model id. Keys are passed per call and never stored by the library; it reads no environment variable for keys. toolChoice is auto or none only, and no temperature is sent.

    Anthropic (Claude)

    • Adapter on the official SDK @anthropic-ai/sdk 1.10.0 (SDK retries off; the layer retries itself).
    • Cache breakpoints on the last tool and the system block; effort always sent explicitly; thinking blocks replayed verbatim.
    • Key shape check: 20–512 printable characters, no spaces. A key starting sk- but not sk-ant- is refused as "That looks like an OpenAI key, not an Anthropic key."

    OpenAI

    • Adapter on the official SDK openai 7.59.0, Responses API, store:false, include:["reasoning.encrypted_content"]; reasoning items replayed verbatim.
    • Key shape check: same length rule; a key starting sk-ant- is refused as "That looks like an Anthropic key, not an OpenAI key."

    Models

    The model registry (providers/registry.ts) is the single edit point. Defaults:

    ProviderClass deepClass fast
    Anthropicclaude-opus-5-5 (default effort high)claude-haiku-5-5 (default effort low)
    OpenAIgpt-6.2-astra (default effort high)gpt-6-luna (default effort low)

    A settings override (models: { deep, fast }) may name only a model of the provider in force that the registry or the versioned price table (2026-11-18) knows: claude-opus-5-5, claude-sonnet-5-5, claude-fable-5-2, claude-haiku-5-5, gpt-6.2-astra, gpt-6.2-sol, gpt-6.1-terra, gpt-6-luna. Anything else is refused with models.deep "…" is not a known Anthropic model (or OpenAI). Effort is one of low, medium, high, xhigh, max; the stored setting defaults to medium. Model ids and prices rest on the vendor documentation fetched on 18 November 2026.

    Secure key entry

    Keys are entered only in System Studio, never in Composer. The Composer property AI API Credential is read-only status. The driver never receives, stores or displays a key, and refuses a whole configuration document if any key in it is credential-shaped (api_key, token, secret, …) or a display string looks like a key (sk-…, Bearer …, long opaque blobs).

    The Studio route behind the key form is PUT /api/monitoring/ai-core/credentials with { property_id, provider, api_key, scope? } (needs monitoring:manage). The key is encrypted with the platform's secret box; every answer carries only provider, ••••last4 and test status. A key can be company-wide or a property override (scope, default property); a property's calls use its override, else the company key. DELETE removes a key; GET lists masked keys (monitoring:view).

    Connectivity test

    POST /api/monitoring/ai-core/credentials/test with { property_id, provider } (monitoring:manage) tests the key the property's calls would use with a token-free call, GET /v1/models on either vendor. It answers ok or the error kind (auth, permission, network, …), never the vendor's message, which can echo the key. Tests are limited to 6 per minute per property (connectivity_test_limit: "Too many connection tests. Wait a minute and try again."). Whether either vendor bills GET /v1/models could not be verified from their documentation.

    From Composer, Test AI Connection asks the platform through cloud op test_provider; the result is delivered later as AI Response Ready.

    Chapter 4

    SmartBuildOS Agent Integration

    The SmartBuildOS Agent (smartbuildos.c4z) is AI Core's only peer on the controller. It authenticates AI Core, routes its messages, relays its cloud ops, forwards its configuration, licenses it and carries its events to the cloud.

    What the Agent does for AI Core

    • Registry and tokens. Registers AI Core as ai_core and issues a per-registration token minted from C4:UUID("RANDOM") when Director returns one (otherwise the v1 generator).
    • Sender stamping. Writes from_module_id / from_instance_id itself; a module's own claim is never forwarded.
    • Cloud relay. POSTs AI Core's cloud ops to /api/integrations/control4/modules/rpc with its pairing token. The platform derives tenant and property from that token only.
    • Configuration. Forwards SBOS_DRIVER_CONFIG for SKU SBOS_AI_CORE; AI Core answers SBOS_DRIVER_CONFIG_ACK.
    • Restricted operations. Delivers the platform's six closed operations as SBOS_MODULE_COMMAND.
    • Durable event path. Queues AI Core's envelopes and uploads them; acknowledges with SBOS_MODULE_EVENTS_ACK.
    • Licensing. Answers the licence SDK (sbos.license) for SKU SBOS_AI_CORE.

    Registration and liveness

    LateInit registers with the v2 manifest (driver sbos.ai_core; AI Core serves no capability to other modules). On SBOS_MODULE_AGENT_HELLO it re-registers (new token) and re-subscribes; on SBOS_MODULE_DIRECTORY_CHANGED it re-reads the directory 2 s later. A liveness probe (SBOS_MODULE_DISCOVER filtered to flight_recorder) runs every 5 min, and every 30 s while the Agent is not answering. A failed probe sets agent_lost and tries to re-register; the first answer flushes the buffer. The probe exists because DriverWorks gives no delivery acknowledgement.

    Connection states

    The driver derives one state; the first matching row wins. AI_STATUS holds the code (or working while jobs are pending).

    agent_update_requiredthe Agent negotiated protocol 1SmartBuildOS Agent update required (module contract v2)
    agent_lostregistered, but the liveness probe got no directory by its deadlineSmartBuildOS Agent not responding

    Every change of state emits one ai_core.status envelope. AGENT_CONNECTED going true → false fires Agent Disconnected; the reason is in AI_LAST_EVENT_DETAIL.

    System Studio owns the configuration. Saving AI Core settings publishes the driver-relevant, non-secret subset through driver_config for SBOS_AI_CORE; the Agent forwards it; the same document can also arrive by the restricted operation apply_config.

One bad field refuses the whole document and the last valid one stays in force; Last Error reads Configuration vN refused: <path>: <reason> (vM kept).

    Restricted operations

    The platform can send exactly six . Each accepts a closed set of argument keys; any other key refuses the whole operation (Failed). States are reported with SBOS_MODULE_COMMAND_RESULT: Accepted, Executing, then Completed / Failed. None controls equipment, runs code or forwards a command name.

    Buffering while the Agent is away

    • Normal path: module client stage (≤ 300, frames of ≤ 100, 30 s ack, 3 tries) → the Agent's durable acknowledged queue → the cloud.
    • No Agent answering: critical envelopes (severity warning or above) go to a persisted buffer of 50 (dedup by event_id, evict least severe then oldest, every drop counted). The rest wait in memory and are lost on restart (counted when dropped). The buffer drains oldest first when the Agent answers again.
    • Telemetry Status shows either Through the Agent: N sent, N acknowledged, N dropped; buffer N, buffer drops N or No Agent answering: N critical event(s) buffered, N waiting in memory, N dropped.

    Licence behaviour

    Commands, run_diagnostic and collection stop only when license.enforces() (a definitive denial with enforcement on). A missing feature refuses only when enforcement is on and the status is authorised. Grace, trial, legacy, cloud-validation-required and no-answer states fail open. A refusal shows in Last Error as not licensed: … or the licence does not include AI_LEARNING.

    Chapter 5

    Flight Recorder Integration

    The SmartBuildOS Flight Recorder is the home's history. Control4 offers drivers no way to read its own History, so AI Core answers "what happened" from Flight Recorder events: cloud-side for the AI, and from the recorder's recent local ring for diagnostics on the controller.

    Why the Flight Recorder matters

    Without it, AI Core cannot see Composer device events at all (it would need the recorder's per-driver event catalogue, and duplicating it would be the double capture the architecture forbids). With it, AI Core reads device events, variable changes and programming traces through topic subscriptions and records only what the recorder does not.

    What is collected, and by whom

    AI Core's own system events are the documented ids only: 17 OnNetworkBindingAdded, 18 OnNetworkBindingRemoved, 19 OnNetworkBindingRegistered, 20 OnNetworkBindingUnregistered, 48 OnDeviceOnline, 49 OnDeviceOffline, 90 OnDirectorIPAddressChanged. Consumed recorder events are not re-uploaded; they already reach the cloud through the recorder. Before anything is recorded the collector applies, in order: learning paused or licence halted → nothing; excluded room; excluded category; event-id dedup (ring of 512); per-minute budget (own observations only).

    Local history (on the controller)

    The Flight Recorder advertises four request and one topic capability. Only AI Core may request them (policy table, Chapter 6). Correlation, incident analysis and period comparison are not served locally; they are cloud tools.

    Each local event carries its event_id (the envelope id the platform stores) or no_event_id (over_upload_budget: held locally but never uploaded; not_recorded: recorded before ids were kept). truncated = true says older matching entries may have existed but are no longer held. Answers are never synthesised.

    Local diagnostics

    AI_START_DIAGNOSTIC (or run_diagnostic) asks the recorder for events.device_history {device_id, limit: 25} or events.room_activity {room_id, limit: 25} (timeout 10 s, 1 retry) and records one ai_core.diagnostic envelope. Its note says local Flight Recorder history only; causes are not inferred on the controller. With nothing to attach it says why: flight_recorder_not_installed, flight_recorder_has_no_local_history_service, flight_recorder_unknown_agent_cannot_discover, or request_failed with error_code.

    History in the cloud

    For the AI, history is read from the platform's flight_recorder_events table through seven read tools (flight_recorder_search_events, flight_recorder_get_timeline, flight_recorder_get_device_history, flight_recorder_get_room_activity, flight_recorder_correlate_events, flight_recorder_analyze_incident, flight_recorder_compare_periods). Gaps (no data, retention edge, dropped events, stale Agent, clock-suspect events) are listed, never filled in. A shared correlation id is a confirmed link; same device or room within a time window is only possible. Full schemas are in Developer Reference.

    Retention

    DataDefault retention (platform)
    Events30 days from receipt
    Traces and steps90 days
    Snapshots30 days

    The detectors depend on this: seasonal patterns always answer insufficient_history (they need ≥ 365 days), and an "unused scene" needs 90 observed days of scene recording.

    Limitations

    • The local ring is short and bounded; local answers page with a cursor (pages ~20 KB, hard cap 24 KB). A cursor is refused after Clear Local History.
    • Local pub/sub is best-effort, at-most-once, bounded at 200 envelopes per subscription (drop-oldest, counted).
    • Variables whose names contain codes or credentials (USERCODE, PASSWORD, TOKEN, …) are never recorded; payloads are redacted on the controller and again on the platform.
    • Homeowner portal access to Flight Recorder tables is not granted.
    • An old (v1) recorder, or one AI Core cannot discover, is treated as present: AI Core does not duplicate its classes.

      Chapter 6

      Driver-to-Driver Integration

      DriverWorks gives drivers no sender identity, no broadcast and no delivery guarantee. Module contract v2 supplies them, hub-and-spoke through the SmartBuildOS Agent: discovery, local pub/sub, module-to-module requests, and a closed-vocabulary cloud relay. It is a strict superset of v1, so v1 modules keep working.

      The model

      Every frame is C4:SendToDevice(id, COMMAND, params) into the receiver's ExecuteCommand. Params are strings; structured data is JSON in one param. Module → Agent frames carry the v1 auth triple (module_id, instance_id, token); the Agent ignores, without answering, any frame that fails authentication. Agent → module frames carry the recipient's triple, so another driver cannot inject answers. Negotiation: both sides support PROTOCOL_MIN = 1, PROTOCOL_MAX = 2; AI Core requires 2 and reports agent_update_required against a v1-only Agent.

      Capability discovery

      SBOS_MODULE_DISCOVER (optional filter {module_id?, capability?}) is answered by SBOS_MODULE_DIRECTORY: the Agent's state (version, protocol_min, protocol_max, paired, connected) and every registered module (module_id, instance_id, driver, driver_version, protocol, status, stale, capabilities[]). Modules not heard from for 15 minutes are stale. Tokens are never included. When a module registers, unregisters or goes stale, the Agent pushes SBOS_MODULE_DIRECTORY_CHANGED 5 s after the first change of a burst. Consumers discover; they never assume.

      Registration and the capability manifest

      SBOS_MODULE_REGISTER takes an optional manifest (JSON ≤ 2 KB, ≤ 24 capabilities). A malformed manifest does not fail registration; the reply carries manifest_error (invalid_manifest, manifest_too_large, too_many_capabilities, invalid_capability). A capability a driver cannot serve locally must not be advertised.

      {
  "driver": "sbos.flight_recorder",
  "version": "20261118.120000",
  "protocol": 2,
  "capabilities": [
    { "id": "events.query", "version": 1, "kind": "request" },
    { "id": "events.subscribe", "version": 1, "kind": "topic",
      "topics": ["capture.", "observation.", "trace."] }
  ]
}

      Subscriptions

      SBOS_MODULE_SUBSCRIBE (subscription_id, topics: 1–16 ) is answered by SBOS_MODULE_SUBSCRIBED (ok, reason, granted, refused). The Agent fans out only envelopes it accepted, in SBOS_MODULE_PUBLISH frames (≤ 25 envelopes, 1 s after the first buffered one, with a dropped count). At most 8 subscriptions per instance. Subscriptions live in Agent memory and are re-sent after every registration.

      Request / response

      The requester sends SBOS_MODULE_REQUEST (request_id, idempotency_key, to, capability, args ≤ 16 KB, deadline ≤ now + 60 s). The Agent acknowledges with SBOS_MODULE_REQUEST_ACK (Routed or Refused with a code), forwards the request to the target with the stamped sender, and relays the target's SBOS_MODULE_RESPONSE (status, error_code, result ≤ 24 KB, optional cursor). Only the instance the request was routed to may answer. Retries use the same : the Agent replays a stored answer (replayed = "true") instead of routing it twice.

      Retry rules (client library): only deadline_exceeded, target_unavailable, rate_limited and cloud_unreachable are retried — at most 2 retries, after 2 s then 5 s, with the same key and a fresh request_id.

      Command authorization (policy tables)

      The Agent holds closed policy tables; the platform mirrors them in src/lib/ai-core/protocol.ts. Anything not listed is not_permitted. Changing them is a driver release.

      TableEntries
      MODULE_REQUEST_POLICYevents.query, events.timeline, events.device_history, events.room_activity: provider flight_recorder, requester ai_core
      MODULE_TOPIC_POLICYcapture., observation., trace. → subscriber ai_core
      MODULE_CLOUD_OPS.ai_coreask, analyze_room, analyze_system, learn_preference, suggest_scene, generate_report, start_diagnostic, send_notification, set_context, status, test_provider

      Rate limits per module: 30 requests/min (REQUEST and DISCOVER), 20 cloud requests/min, burst 10; at most 128 routes in flight in the whole Agent.

      Adding future drivers

      1. Choose a module_id (^[a-z][a-z0-9_]{2,47}$) and an owned event-type prefix; reserved prefixes today: health. (guardian), test. (commissioning_inspector), mode. (home_state), bridge. (property_bridge).
      2. Use the shared client (sbos.moduleclient) with a manifest that lists only what the driver can really serve, and require_protocol = 2 if it needs v2.
      3. Add rows to MODULE_REQUEST_POLICY / MODULE_TOPIC_POLICY / MODULE_CLOUD_OPS in the Agent and in protocol.ts together; the cross-repo parity test compares them.
      4. Answer every request exactly once with a closed-vocabulary error code; page large results with a cursor.
      5. Prove each guard by breaking it once and watching a test fail, then run the Director-emulator scenario. Bench validation on hardware is still owed for everything in v2.

      Known limits: no global ordering; module identity at registration is still a self-claimed module_id (the token proves the frame came from the registered instance, not that the driver is genuine); legacy Composer commands to the Agent (SEND_EVENT, REPORT_*, SEND_PUSH_NOTIFICATION) remain sender-unverified because programming has no token.

      Chapter 7

      Household Learning

      AI Core learns routines and preferences only when the homeowner allows it, from deterministic detectors with sample-size confidence. The language model phrases findings; it does not invent them. Learning is off by default, and the homeowner can pause, exclude, correct, export and erase.

      How it learns

      The analyze_property job reads stored events, applies the homeowner's controls (pause, exclusions, erase watermark) before any detector, and runs 14 pure detectors:

      DetectorEvidence threshold
      scene_override, thermostat_override≥ 10 activations, rate ≥ 40 %
      daily_routine≥ 15 of the last 30 days, 60-minute local window
      weekly_routine≥ 4 weeks, ≥ 75 % of that weekday
      unused_scene90 observed days of scene recording, 0 activations (today always insufficient_context: no scene inventory exists)
      device_failure≥ 8 offline transitions within 7 days
      frequent_room≥ 50 events, ≥ 7 days, ≥ 15 % share
      lighting_level, shade_preference, media_volume, media_source≥ 10 samples, ≥ 5 days, modal share ≥ 40 %
      favourite_scene≥ 10 activations, ≥ 5 days, ≥ 20 % share
      automation_conflict≥ 10 change-and-revert within 120 s on ≥ 3 days (labelled possible)
      seasonal≥ 365 days of history (not built in v1; answers insufficient_history)

      Thresholds marked "AI Core v1" in the source (weekly routine, frequent room, preferences, favourite scene, automation conflict, seasonal) are this phase's choice and await architect/owner review. Analysis runs on demand (POST /api/monitoring/ai-core/patterns {action:"analyze"}), idempotent per property per 10 minutes; no schedule exists — scheduling is an owner decision.

      Confidence scores

      n = sample size, T = the detector's evidence threshold, c = consistency in [0,1]
n < T          → no finding (never rounded up)
confidence     = c × n / (n + T)       0.5·c at threshold, → c as n grows
band           = low (n < 2T) · medium (n < 4T) · high (n ≥ 4T)

      The band comes from sample size alone. For a fixed consistency the score strictly increases with the sample size.

      Preference memory

      Memories are structured rows with full-text search (no vector store in v1), in four categories: system, explicit_preference, behavioral, operational. Each is verified or inferred (kept in its own column) and records its source: homeowner_stated, staff_entered, detector or registry. The AI reads them with the memory_search tool, which is household data and needs the AI_LEARNING feature. Staff can add a verified fact (POST /api/monitoring/ai-core/memories), never an inference and never a person.

      From Composer, AI_LEARN_PREFERENCE sends cloud op learn_preference. When the platform's memory library is wired it records the statement as a verified explicit preference (source programming) and answers completed at once: no job is tracked and AI Response Ready is not fired for it. Without it the platform answers unsupported.

      In a conversation the AI may call memory_propose to propose one memory. A proposal is stored as pending, is not used for anything, and waits for the homeowner or the integrator to accept or reject it; it never describes a person.

      Behavioural analysis — what the data cannot support

      • Occupancy: device interactions are not occupancy. Room findings are interaction_based unless a motion/occupancy sensor was the source.
      • Who caused a change, and the value before: not recorded; override and conflict statements say so.
      • Security, locks, access: never learned from; no enable switch exists.
      • Away / vacation recommendations: not generated in v1.
      • No time zone: time-of-day detectors answer insufficient_context rather than use UTC.
      • Identity: no finding has a person field; inferred text is scanned for person-implying words. Residual limit: a room or device label an installer named after a person ("Emma's Room") passes through as the label.

      Correcting assumptions

      The homeowner reviews everything learned, inferred items included, with confidence and evidence, through /api/portal/ai-core/memories:

      • PATCH { property_id, memory_id, action: "correct", value, statement? } — a verified preference supersedes the inference.
      • PATCH { …, action: "assign_to_me" } — links the homeowner's own stated preference to their profile (the only way a profile is ever set).
      • DELETE ?property_id=&memory_id= — content erased; a content-free key stops the same inference being re-learned.

      Staff can dismiss a recommendation (PATCH /api/monitoring/ai-core/recommendations/[id] { to: "dismissed" }).

      Privacy settings

      • Off by default. learning_enabled defaults to false.
      • Pause and exclusions: PATCH /api/portal/ai-core/learning { property_id, paused?, excluded_room_ids?, excluded_categories? }. While paused, the driver collects nothing and releases its subscriptions and listeners; Learning Status reads Paused by <who>: <reason>.
      • Export: GET /api/portal/ai-core/learning?property_id=&export=1 returns every piece of AI Core learning data about the property as JSON.
      • Erase all: DELETE /api/portal/ai-core/learning { property_id, confirm: "erase" } deletes memories, patterns and recommendations and sets a watermark so earlier events are never analysed again. Flight Recorder's own history is a separate store and is not deleted; it ages out under its own retention.
      • Household gate: staff need homecontrol:view in addition to monitoring:view to read household activity. Homeowner controls do not require the licence.
      • Recommendations are not customer-visible by default (customer_visible false); only staff can change it.

      Chapter 8

      Intelligent Automation

      AI Core can suggest scenes, recommend HVAC and lighting changes, and propose device actions. It never decides on its own: a deterministic permission engine authorizes every tool call, a person approves every action that is not covered by a homeowner-consented rule, and approved actions run through the existing SmartBuildOS command queue.

      The principle: the model proposes, deterministic code decides

      The language model only emits typed tool calls. Each tool is declared once with a ; the engine reads the risk from the registry, never from the model. No tool accepts Lua, shell, SQL, raw device commands or free-form command names. Each property has a , set in System Studio and shown read-only in Composer: observe (default), recommend, or execute_low_risk. Raising the mode needs homecontrol:manage as well as monitoring:manage.

      Suggested scenes

      AI_SUGGEST_SCENE (ROOM, OCCASION ≤ 120) asks for a suggestion; the result is delivered with kind scene_suggestion into AI_LAST_RESPONSE. It is a suggestion only: nothing is changed. Recommendations generated from learned patterns use the kinds lighting_scene_update, hvac_schedule, entertainment_scene, automation_conflict, away_settings, predictive_assist and service_maintenance (away settings are not generated in v1). A recommendation moves new → reviewed → approved → implementing → implemented, or is dismissed / expired (after 14 days). Recommendations never execute anything; the event Recommendation Available and AI_RECOMMENDATION_COUNT tell programming one is waiting.

      The AI can propose activating an existing scene with actions_activate_scene (scene_id), a low-risk action.

      HVAC

      actions_set_thermostat proposes one setpoint: device_id, mode (heat, cool or single, naming which setpoint) and setpoint_f between 60 and 85 °F. A value outside the bounds is refused, not repaired. The thermostat_override detector looks for setpoints that are repeatedly changed after a schedule (thermostat schedules are not visible; a change marked scheduled is used, otherwise a time recurring on ≥ 15 days stands in, flagged schedule_inferred_from_recurrence).

      Lighting

      actions_set_light proposes one light level, device_id and level 0–100. The lighting_level detector learns a preferred level per device. A low verb aimed at a device the registry does not show as that verb's kind (for example SET_LIGHT on a lock, or an unknown type) is escalated to high risk.

      Approval workflows

      Every action is recorded in ai_core_actions and moves through a fixed lifecycle, enforced by code and again by a database trigger:

      proposed ─┬─ deny ─────────────────────────────────────→ denied
          ├─ require_approval → pending_approval ─┬─ approve → approved
          │                                       └─ deny / cancel / expire
          └─ allow (low + matching consented rule) → approved
approved ─── enqueue → queued ─── the queue's own outcome → completed | failed | expired | denied
      • Who approves. Low-risk actions a person asked for are confirmed by that requester; staff may approve only those (POST /api/monitoring/ai-core/actions/[id], needs homecontrol:manage). Lock, garage and security are the homeowner's alone (POST /api/portal/ai-core/actions).
      • What was seen is what runs. An approval carries args_hash, the hash of the action as the approver saw it.
      • Timing. A proposal waits 30 minutes for approval; the queue adds its own 1 hour after enqueue. At most 10 open actions per property; at most 6 proposals a minute and 40 an hour.
      • Outcome. completed and failed come only from the linked control4_commands row (a real driver acknowledgement), never from AI Core. The platform can raise Approval Required, Action Completed and Action Failed in Composer.
      • Pre-approved rules. In execute_low_risk, a low action runs without a per-action approval only when a rule covers it exactly: verb (SET_LIGHT, SET_THERMOSTAT or ACTIVATE_SCENE only), device or room scope, numeric bounds, allowed values, optional time window, not expired. Staff create rules (POST /api/monitoring/ai-core/rules); a rule is inactive until the homeowner consents in the portal (POST /api/portal/ai-core/rules { decision: "consent", content_hash }) and can be revoked at once.
      • Programming changes are never executed. They become a programming hand-off that a person carries into Composer Studio under their own session (states accepted, in_composer, completed, rejected, withdrawn).

      Safety limitations

      • observe denies every non-read class: the AI may not even ask.
      • Locks, garage doors and security partitions always need explicit homeowner approval per action, are never automatic, and are never proposed on learned behaviour alone. A disarm code is never taken by AI Core; approving sends the action on to the queue's own Control4 approval, a second separate confirmation that collects any code.
      • The homeowner's Composer Remote Control tier on the Agent still bounds what is possible: low verbs need the controller capability comfort_v1 (Comfort) and lock/garage/security need control_v1 (Full control).
      • No tool can read a credential: there is no credential risk class.
      • A physical device change from an approved AI action has not been demonstrated: it needs a controller (checklist 7.9).

        Lifestyle Concierge

        The concierge — restaurant reservations, calendar entries and the approvals around them — is in development and not available in this release. This chapter describes the design being built, so dealers know what to expect, and exactly what blocks each part. Nothing here can make a real booking today.

        What is being built

        • Concierge tools gated by the licence feature AI_CONCIERGE: concierge_list_providers, concierge_list_services, concierge_suggest_reservation, concierge_search_places, concierge_search_availability, concierge_present_options, concierge_submit_booking, concierge_check_booking, concierge_calendar_list, concierge_calendar_add, concierge_offer_scene. Only concierge_submit_booking and concierge_calendar_add are in the external risk class; the rest read or record suggestions.
        • The permission engine's external rule (Completed in simulation, 7.1): explicit homeowner confirmation always; denied in observe, for an automation, and on learned behaviour alone.
        • A provider registry whose only usable provider is the sandbox, named SIMULATION — SmartBuildOS sandbox restaurants, which staff turn on per property. Its bookings end as simulated_confirmed, never confirmed, and are never written to a real calendar.

        Reservations

        Every request follows a fixed state machine, enforced in code and again by a database trigger. Each step names who may take it; the homeowner's steps exist only in the portal route.

        suggested ──(homeowner approves the search)──→ search_approved
search_approved ──(search + presentation)──→ options_presented
options_presented ──(homeowner picks one)──→ option_selected
option_selected ──(server builds the exact details)──→ details_presented
details_presented ──(homeowner confirms THESE details, by hash)──→ final_confirmed
final_confirmed ──(submission, idempotent)──→ submitted
submitted ──(the provider's own getBooking)──→ confirmed | simulated_confirmed | failed
failed ──(homeowner: retry | stop)──→ submitted | cancelled
anything open ──→ cancelled (homeowner) | expired (system)

        A suggestion based on learned behaviour can never go further than a suggestion without the homeowner's approval. Real providers are adapter slots, each blocked as follows:

        ServiceBlocked on
        OpenTablePartner approval and a formal agreement
        Yelp ReservationsYelp partner enablement (partner-only, disabled by default)
        SevenRoomsPartnership / venue-provisioned credentials

        Reserve with GoogleNot applicable: a provider-side programme, not a consumer booking API

        Scraping or driving consumer booking sites with an agent is prohibited regardless.

        Calendar

        Google Calendar and Microsoft Graph adapters with homeowner OAuth are being built against the real APIs (9.3, In progress). The homeowner connects a calendar in the portal (/api/portal/ai-core/calendar, connect and callback per provider) and separately allows the assistant to read it; disconnecting deletes the stored tokens. Writing is only ever an offer (concierge_calendar_add) that the homeowner confirms in the portal. Real calendar use is blocked on OAuth client credentials; Google's calendar scope is a sensitive scope that needs Google verification before production. Restaurant discovery through Google Places (concierge_search_places, search only, no booking) needs an API key.

        Approvals

        The homeowner approves the search, picks an option and gives final confirmation of the exact details (by details_hash) through POST /api/portal/ai-core/concierge actions (create, approve_search, search, select_option, confirm, submit, check, recover, cancel, add_to_calendar, answer_scene_offer). The model can submit only what the homeowner already confirmed. Staff have a read-only view and cannot move a request. The portal screens are not started (9.4).

        Confirmation

        Only the provider's own answer (getBooking) can make a request confirmed; a sandbox booking is simulated_confirmed and is labelled as a simulation (9.5, In progress).

        External services

        concierge_list_services reports what each area (reservations, household services, entertainment, travel, events, shopping, guest preparation) can and cannot do. Today no real external service is integrated; only Google Places discovery and the two calendar APIs are built against real APIs, and each needs credentials that do not exist yet.

        Failed-booking recovery

        A failed submission waits for the homeowner: retry (submits again), alternatives (a new request; the failed one is stopped) or stop. This is in progress (9.5).

        Chapter 12

        Security

        The controller stays light and holds no secrets; the cloud authorizes every tool call with deterministic code; household activity is a second gate; and the homeowner keeps control of what is learned.

        Credential storage

        • Provider keys are customer-supplied and entered only in System Studio. They are stored as secret-box ciphertext in ai_core_provider_credentials; answers carry only provider, ••••last4 and test status.
        • Keys never transit the controller. The driver refuses any configuration document containing a credential-shaped key or a display string that looks like a key.
        • The provider layer removes key material from every string that leaves it; connectivity tests return an error kind, never the vendor message.
        • The Agent's pairing token authenticates its cloud calls; module tokens never leave the controller.
        • No AI tool can read a secret: the credential risk class has no tool and is refused by the engine.

        Permissions

        The permission engine (src/lib/ai-core/authz/engine.ts) is pure, synchronous and total: every input it does not recognise is a denial. Its inputs are built by the server from the session — actor, property permission mode, tool (risk, household flag, verb, feature), target (device type from the registry), controller capabilities, entitlement features, pre-approved rules, learning basis and the route gate's would-deny flag.

        • All AI Core tables (ai_core_*) carry a composite foreign key to the property, have row-level security on, and grant access only to the service role (revoke-first).
        • Device ids are validated against the property's registry; a homeowner can act only on their own client's properties; own-scope staff roles see only their clients' properties (anything else is 404).
        • Idempotency keys are unique; replays are refused; per-property rate limits live in the database.
        • Cross-property and cross-tenant isolation tests pass in simulation (7.5).

        Approval policies

        See Chapter 8. In short: low actions — the requester (or the homeowner for automations and learned behaviour), unless a consented rule covers them in execute_low_risk; high and external — the homeowner, per action; programming — a person in Composer Studio.

        Audit

        ai_core_audit_events is append-only. The orchestrator writes turn.started, provider.call, budget.refused, turn.round_limit and answer.invalid; every tool call records its decision; credential changes are recorded (e.g. credential.deleted). The audit trail for every tool call and decision is Completed in simulation (7.7).

        Privacy controls and prompt-injection defence

        • Household activity needs homecontrol:view in addition to the route gate; learning can be paused, scoped and erased by the homeowner (Chapter 7).
        • The system prompt is a static constant that contains no tenant data; telemetry reaches the model only inside tool results marked {"untrusted":true,"source":…,"data":…}.
        • The tool list is fixed before the first round and does not change because of anything a tool returns. A call the model was talked into by injected text is refused by the engine like any other. Prompt-injection tests with hostile device names, titles and calendar text pass in simulation (7.6).
        • A historical answer with no surviving evidence is replaced in full by I don't have evidence for that.
        • OpenAI calls use store:false.

        Extension guidelines

        1. Extend, do not fork. Use the module contract, command queue, Flight Recorder store, licensing, notifications, audit and secret box that exist.
        2. New tool: defineTool with a dotted lower-case id, a wire name matching ^[a-zA-Z0-9_-]{1,64}$, a declared risk (read, low, high, external, programming), a declared household flag, a closed object schema (additionalProperties: false), and — for any action tool — a resolveTarget that reads the target from the registry. There is no way to declare a credential risk.
        3. New cloud op or capability: add it to the Agent policy table and protocol.ts together; it is a driver release.
        4. New Composer event: append an id (ids are permanent) and add its key to raise_event's closed list on both sides.
        5. Evidence: any historical claim must cite event ids a tool returned in the same turn.
        6. Prove guards: a thing is tested only when a test that fails without it passes.
        7. Label simulations as simulations in code, UI, tests and docs.
