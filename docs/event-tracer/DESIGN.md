# Event Tracer — design

> **Merged into the Flight Recorder on 11 November 2026.** The Event Tracer is
> no longer a driver of its own: its capture engine (`src/tracer/*`, unchanged
> apart from history notes) runs inside `smartbuildos-flight-recorder`, under
> the module id `flight_recorder` and the SKU `SBOS_FLIGHT_RECORDER`. The
> event types `capture.*` and `tracer.*` kept their names. Property, action
> and command names changed (Capture → Event Capture, Coverage → Event
> Coverage, `MARK_TIMELINE` → `RECORD_EVENT`, …): the Flight Recorder manual
> has the current ones. What follows is the record as it was written for the
> separate driver.

Status: implemented on driver branch `feat/event-tracer` (from
`feat/flight-recorder`); simulator-verified (`make test`); **bench validation
owed** (`VERIFICATION.md`). Date: 2026-11-09.

## The problem it solves

"Why did the hall light come on at 3 am?" Today the dealer opens Composer Pro,
reads the programming, and guesses. Director gives a driver no record of which
programming ran — but it will deliver every Composer **event** every device
fires, once a driver asks for it by (device id, event id). The Event Tracer
asks for all of them, with **no configuration**, and keeps the sequence: the
keypad press, the contact change, the Agent's reconnect, in the order they
happened, named the way Composer names them.

It does not replace the Flight Recorder; it fills the one row Flight Recorder
v1 declared unsupported (CAPABILITY-MATRIX row 7, "other drivers' Composer
events … NOT used" because nothing enumerates them). The two are siblings on
the same Agent pipeline:

| | Flight Recorder | Event Tracer |
| --- | --- | --- |
| Records | selected **variable values** (state), programming traces, snapshots | every **Composer event** of every device (what fired) |
| Configuration | per-source, from Studio or templates | none; exclusions and bounds only |
| Evidence | observed / requested / instrumented | observed (events), instrumented (marks) |
| Prefixes | `observation.` `trace.` `recorder.` `snapshot.` | `capture.` `tracer.` |
| SKU | `SBOS_FLIGHT_RECORDER` | `SBOS_EVENT_TRACER` |
| module_id | `flight_recorder` | `event_tracer` |

Merging later is cheap: Flight Recorder's config schema reserved
`kind = "device_event"`; `src/tracer/*` is pure and could serve as that kind's
implementation. Shipping it as its own driver first keeps the zero-config
promise and the SKU story simple.

## Why a driver has to know the event ids first

`C4:RegisterDeviceEvent(deviceId, eventId)` subscribes to ONE event id. No
documented call lists a device's events (census over 123 readable shipped
drivers: `GetDeviceEvents` appears in none). So the tracer carries a
catalogue, three tiers, best first (`src/tracer/catalog.lua`):

| Tier | Source | Covers | Evidence |
| --- | --- | --- | --- |
| `project` | `C4:GetProjectItems("DEVICES", "NO_ROOT_TAGS")` — the project **without** `LIMIT_DEVICE_DATA`; each `<item>`'s `<itemdata>` parsed for `<events>` | Control4's own `.c4i` drivers, which are never in a dealer's library | **PROBE.** The Agent only ever reads the limited form (measured shape `<itemdata><driver>x</driver><state/></itemdata>`). Whether the unlimited form carries `<events>` is the first bench question. Property **Catalogue** reports `project: N device(s)`; N = 0 means the OS strips it and the other tiers carry on. Size-capped at 6 MB. |
| `builtin` | `src/tracer/catalog_data.lua`, generated by `tools/gen-event-catalog.py` from `~/Documents/Control4/Drivers` (406 files → 187 drivers declare events → 1,303 events, 42 KB) | every third-party driver in the owner's library; regenerate when the library grows | VERIFIED_BY_EXAMPLE: `driver.xml` is plain text inside every `.c4z`, encrypted Lua or not |
| `learned` | event ids that arrived on a **probe** subscription, persisted (`et_learned_v1`) | drivers in no catalogue, after one occurrence | MEASURED under the shim; bench owed |
| `probe` | ids 1..**Probe Range** (default 32, ceiling 64) on devices no tier knows, **opt-in** (Probe Unknown Drivers = On) | discovery | PROBE: whether registering a non-existent event id is harmless on-controller is unmeasured (the vendored wrapper only validates types). Opt-in until measured. Ids above 200 (the C4-V-* lights use 200–202) are out of probe reach by design — the catalogue covers those. |

Names are what the driver's own XML declares — exactly what Composer shows.

## What is recorded, where

Every subscribed event becomes one timeline **entry** `{ t, device_id,
device_label, room_id, room_label, driver, event_id, event_name, known }`:

- **Local ring** (`src/tracer/ring.lua`): newest *Local History Size* entries
  (default 500, 50..2000), monotonic `seq`, checkpointed to ONE persist key
  every 30 s when dirty and on destroy, restored at start. *Print Recent
  Events* and *Print Events For Inspect Device* read it from Composer's Lua
  output — no Pro session, no cloud. Loss window on a hard power cut: ≤ 30 s.
- **Pipeline**: a `capture.event` envelope (evidence `observed`, quality
  `confirmed` when the name is known, `unknown` when it is a placeholder) in
  the Agent's durable queue → SmartBuildOS → Studio. `capture.mark` for
  Composer markers (evidence `instrumented`, quality `unreviewed_text`).

### What is NOT claimed

Director does not tell a driver which programming ran, nor whether a human or
an automation caused an event. An entry says WHICH device fired WHICH event
WHEN. The "why" is the sequence of entries around it. Studio may draw a
window around a mark; it must not label a cause. `OnDeviceEvent` carries no
parameters, so no event payload is recorded either.

## Protection (the rules a technician relies on)

| Rule | Behaviour | Default / ceiling |
| --- | --- | --- |
| Storm | the same event from the same device ≥ *Storm Threshold* times inside a 60 s window → one `tracer.storm` (warning) + Composer event *Event Storm Detected*; further occurrences that minute are **counted, not recorded** (not in the ring either); when the minute rolls (next event or the 30 s tick) `tracer.storm_ended` carries `count` and `suppressed` + *Event Storm Ended* | 30 / 600; 0 disables |
| Upload budget | envelopes beyond *Upload Budget* per minute are dropped and counted, one `tracer.budget_exceeded` per minute. The **ring is not budgeted** (bounded by size), so local history can show what the uplink missed | 300 / 1,200 per minute |
| Subscription cap | devices covered in ascending id order until *Max Subscriptions*; the rest counted per device (`unsubscribed`) and reported in Coverage — never silently skipped | 1,000 / 2,500 |
| Exclusions | *Exclude Device IDs*, *Exclude Driver Files*; the tracer's own device is never a source | ≤ 200 each |
| Reconciliation | apply() registers/unregisters only the difference; identical re-apply touches nothing; `project_changed` / `director_reloaded` (forwarded by the Agent) and the Agent's own registration re-plan after a 5 s quiet period | — |
| Licence | `license.enforces()` (definitive denial AND enforcement on) releases every subscription and paints `unlicensed`; any uncertain status leaves capture running (charter: fail open) | — |
| Pause | releases every subscription; persisted; resume re-plans. "What fired while paused is not known" is said in the event | — |

Policy comes from Composer properties (validated per field: a bad value is
ignored, named in *Last Capture Error*, and never stops capture) or from a
Studio `apply_policy` command / `SBOS_DRIVER_CONFIG` settings document with the
same keys, which is written INTO the properties (see "Platform side"). A later
Composer property change wins (one truth: the properties).

## Resource model (what the bench must confirm)

- **Registrations.** A 300-device project with ~7 events each is ~2,100
  `RegisterDeviceEvent` calls at apply. Max concurrent device-event
  registrations per driver is UNMEASURED; the cap (default 1,000) exists for
  that reason, with Coverage saying what did not fit. Bench: raise the cap on
  Beta 1 and watch Director's memory and apply time.
- **Callback cost.** One `OnDeviceEvent` = table lookup, ring push, optional
  envelope build, stage. The vendored `handlers.lua` `OnDeviceEvent` prints on
  every call; the driver installs its own.
- **Property churn.** *Last Event* / counters paint at most once per 2 s
  (coalescing timer) plus the 60 s full paint — not per event.
- **Project XML.** Read on apply only (start, project change, policy
  change), size-capped; never continuously.
- **Persist.** Ring checkpoint ≤ 1 write / 30 s; learned catalogue ≤ 1 write /
  5 s after a learn; paused flag on change.

## Composer surface

`<combo>true</combo>` is declared: a proxy-less `lua_gen` driver without it
imports fine and is never listed by Composer's Items search (measured on
Beta Site 2, VERIFICATION.md). Mode Composer and System Link already carry
it; Flight Recorder does not and should.

Properties, actions, commands, events, conditionals and variables are listed
in `drivers/smartbuildos-event-tracer/www/documentation/index.md`. The
standardised licensing properties (License Status / Source, Subscription
Tier, SmartBuildOS Company) are painted by `sbos.license`.

## Platform side (web repo, branch `codex/dealer-tooling-studio`) — built 2026-11-09

Stacked on `codex/flight-recorder` (PR #394); see that repo's
`docs/dealer-tooling/README.md`. Not merged, migrations not applied.

- Catalogue row + SKU `SBOS_EVENT_TRACER` (migration `20261109120000`).
- Prefix ownership `event_tracer → capture., tracer.` in `validateEnvelope`.
- `MODULE_COMMAND` verbs `apply_policy`, `pause`, `resume`, `reapply`,
  `refresh_status`, in the web repo's `MODULE_OPERATIONS` AND in the Agent's
  `MODULE_COMMANDS` (an Agent build before 2026-11-09 20:34 refuses them by
  name).
- Studio: Activity → Event Tracer (timeline with markers and storm rows,
  Storms, Coverage from `tracer.applied`, Capture settings, Driver).

**Studio policy, one truth.** `apply_policy` (and an `SBOS_DRIVER_CONFIG`
document) is a CHANGE: the driver merges the keys sent over the running
policy, refuses the whole document if any field is invalid (nothing falls
back silently when a person is looking at a form), writes the result into
its Composer properties and applies it. So Composer shows what Studio set,
the setting survives a reload, and a later Composer edit wins. Every
`tracer.applied` carries `payload.policy` (`Tracer.policyReport`): the
running policy, exclusion lists cut to 30 entries with their true totals, so
Studio can show it and knows when a list is incomplete.
