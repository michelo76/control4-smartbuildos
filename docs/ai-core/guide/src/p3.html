Chapter 8

Intelligent Automation

AI Core can suggest scenes, recommend HVAC and lighting changes, and propose device actions. It never decides on its own: a deterministic permission engine authorizes every tool call, a person approves every action that is not covered by a homeowner-consented rule, and approved actions run through the existing SmartBuildOS command queue.

The principle: the model proposes, deterministic code decides

The language model only emits typed tool calls. Each tool is declared once with a ; the engine reads the risk from the registry, never from the model. No tool accepts Lua, shell, SQL, raw device commands or free-form command names. Each property has a , set in System Studio and shown read-only in Composer: observe (default), recommend, or execute_low_risk. Raising the mode needs homecontrol:manage as well as monitoring:manage.

Suggested scenes

AI_SUGGEST_SCENE (ROOM, OCCASION ≤ 120) asks for a suggestion; the result is delivered with kind scene_suggestion into AI_LAST_RESPONSE. It is a suggestion only: nothing is changed. Recommendations generated from learned patterns use the kinds lighting_scene_update, hvac_schedule, entertainment_scene, automation_conflict, away_settings, predictive_assist and service_maintenance (away settings are not generated in v1). A recommendation moves new → reviewed → approved → implementing → implemented, or is dismissed / expired (after 14 days). Recommendations never execute anything; the event Recommendation Available and AI_RECOMMENDATION_COUNT tell programming one is waiting.

The AI can propose activating an existing scene with actions_activate_scene (scene_id), a low-risk action.

HVAC

actions_set_thermostat proposes one setpoint: device_id, mode (heat, cool or single, naming which setpoint) and setpoint_f between 60 and 85 °F. A value outside the bounds is refused, not repaired. The thermostat_override detector looks for setpoints that are repeatedly changed after a schedule (thermostat schedules are not visible; a change marked scheduled is used, otherwise a time recurring on ≥ 15 days stands in, flagged schedule_inferred_from_recurrence).

Lighting

actions_set_light proposes one light level, device_id and level 0–100. The lighting_level detector learns a preferred level per device. A low verb aimed at a device the registry does not show as that verb's kind (for example SET_LIGHT on a lock, or an unknown type) is escalated to high risk.

The action lifecycle

Every action is recorded in ai_core_actions and moves through a fixed lifecycle, enforced in TypeScript (actions/lifecycle.ts) and again by a database trigger; a unit test pins the two equal.

FromTo

  • Who approves. A low-risk action a person asked for is approved by that requester, or by staff with homecontrol:manage (POST /api/monitoring/ai-core/actions/[id]). An action with required_approver homeowner, or risk high, is the homeowner's alone (POST /api/portal/ai-core/actions); Studio says Awaiting the homeowner. Lock, garage and security actions are the homeowner's alone to approve; staff cannot approve them here.
  • What was seen is what runs. An approval carries args_hash, the hash of the action as the approver saw it; a mismatch answers 409 approval_mismatch (This action changed since you saw it. Reload it and decide again.).
  • Timing and limits. A proposal waits 30 minutes for approval; the queue adds its own 1 hour after enqueue. At most 10 open actions per property, 6 proposals a minute and 40 an hour (owner decision 9).
  • Outcome. completed and failed come only from the queue row (a real driver acknowledgement), never from AI Core. The platform can raise Approval Required, Action Completed and Action Failed in Composer, with the action id in AI_LAST_CORRELATION_ID.

Locks, garage doors and security: two confirmations

A lock, garage or security action (or any action escalated to high risk by its target class) needs two separate homeowner confirmations: first AI Core's approval in the portal, then the command queue's own Control4 approval, which collects any disarm code. AI Core never takes, answers or pre-fills that second step. The portal says so after the first approval: Locks, garage doors and security ask again: after you approve here, the request appears in Home control requests (under Approvals), where you approve it a second time — and enter your security code if it disarms the alarm. Whether two confirmations should stay is owner decision 9.

Pre-approved rules and homeowner consent

In execute_low_risk, a low action runs without a per-action approval only when an active rule covers it exactly: verb SET_LIGHT, SET_THERMOSTAT or ACTIVATE_SCENE only; a device or room scope; numeric bounds inside the queue's clamp; allowed values (thermostat modes); an optional time window with an IANA time zone; an expiry within 365 days.

  1. Staff create it in Studio › Recommendations › Pre-approved rules (POST /api/monitoring/ai-core/rules, needs monitoring:manage and homecontrol:manage): Save rule (inactive until consent) → Saved — inactive until the homeowner consents.
  2. The homeowner consents in the portal (What the assistant may do without asking › Review and allow), which sends { decision: "consent", content_hash }; a hash that is not the stored rule's answers 409 content_mismatch, so the homeowner consents to exactly what they saw.
  3. Either side can revoke at once (Revoke now in the portal; DELETE in Studio). Revocation is final and never needs the licence.

A rule never covers locks, garage doors or security, and a learned basis never makes anything automatic.

Programming changes: a hand-off carried by a person

AI Core never applies programming. A recommendation that needs a programming change becomes a programming hand-off (Studio › Recommendations › Programming hand-offs; /api/monitoring/ai-core/programming), created only from a recommendation in reviewed, approved or implementing. Its states: proposed → accepted (Accept — I will carry this into Composer) → in_composer (needs a Composer project or reference) → completed, or rejected / withdrawn. Moving it to accepted, in Composer or completed needs the person's own Composer Studio edit permission. The page states: AI Core never edits Composer programming, never writes a blueprint and never records a checkpoint. Composer Studio has no per-project programming field, so nothing can be accepted into a blueprint automatically (owner decision 10).

Safety limitations

  • observe denies every non-read class: the AI may not even ask.
  • Locks, garage doors and security partitions always need explicit homeowner approval per action, are never automatic, and are never proposed on learned behaviour alone. A disarm code is never taken by AI Core; approving sends the action on to the queue's own Control4 approval, a second separate confirmation that collects any code.
  • The homeowner's Composer Remote Control tier on the Agent still bounds what is possible: low verbs need the controller capability comfort_v1 (Comfort) and lock/garage/security need control_v1 (Full control).
  • No tool can read a credential: there is no credential risk class.
  • A physical device change from an approved AI action has not been demonstrated: it needs a controller (checklist 7.9).

    Lifestyle Concierge

    The concierge lets a homeowner plan a restaurant reservation with the assistant and approve every step. As built, the only provider that can complete a request is a labelled SIMULATION sandbox, which staff switch on per property: nothing is ever booked at a real restaurant. Real vendors, calendars and Places discovery are each blocked on something outside engineering, and this chapter says what.

    What exists

    • Eleven concierge tools, offered only in a homeowner's portal conversation and gated by the licence feature AI_CONCIERGE: concierge_list_providers, concierge_list_services, concierge_suggest_reservation, concierge_search_places, concierge_search_availability, concierge_present_options, concierge_submit_booking, concierge_check_booking, concierge_calendar_list, concierge_calendar_add, concierge_offer_scene. Only concierge_submit_booking and concierge_calendar_add are in the external risk class; the rest read, or record something for the homeowner to act on. Approving the search, choosing an option, final confirmation and recovery choices have no tool: they exist only as the homeowner's own portal actions.
    • A request state machine enforced in code and again by a database trigger (below).
    • A provider registry that lists every vendor with its true status, an adapter only for the sandbox, and a database that admits only the sandbox as a provider.
    • Google Calendar and Microsoft Graph adapters with homeowner OAuth (PKCE, encrypted tokens), and Google Places search — built against documented wire shapes and never called live.
    • The portal's Concierge and Calendar areas in Your home assistant, and a read-only staff view with the sandbox switch.

    Approvals and the portal actions

    The homeowner's steps are actions on POST /api/portal/ai-core/concierge (30 a minute): create {criteria} (suggests and approves the search in one step), approve_search, search, select_option, back_to_options, search_again, confirm {details_hash, submit?}, submit, check, recover, cancel, add_to_calendar, answer_scene_offer.     Confirmation

    Only the provider's own answer can make a request confirmed. A submission is never assumed: a created booking is verified with getBooking before it is settled; a timeout or unknown error is resolved by asking the provider; while it is unanswered the card reads Sent … not yet confirmed with Check with the provider. A sandbox request settles as simulated_confirmed with a SIMULATION reference (not a real confirmation).

    Failed-booking recovery

    A failed request waits for the homeowner, who chooses among the recovery options the failure allows (concierge/service.ts recoveryFor):

    Control4 Programming

    Everything AI Core exposes to Composer: 11 commands, 4 actions, 23 properties, 10 events, 11 variables and 5 conditionals. The tables below are generated from the same data the Command Reference uses, which a test compares name for name with driver.xml.

    Commands and programming parameters

    Parameters arrive as strings. Every value is validated; typed text over its limit is refused, not cut. Lengths are counted in characters (Unicode code points), as the platform counts them. A refused command sends nothing and sets Last Error, AI_LAST_ERROR and AI Status (refused locally (<code>)). At most 10 commands a minute; the 11th is refused rate_limited. ROOM is a room name or id (a STRING, not a room selector), resolved against the devices in the project; a typed ROOM longer than 64 characters is refused (… (use the room id)). LIST labels normalise to codes (Last 7 Days → last_7_days); an empty optional LIST takes its default, an empty required one is refused <PARAM>: is required. A command whose room (or whose device's room) is excluded in System Studio is refused not_permitted, except AI_ASK and AI_SEND_NOTIFICATION (the cloud decides those).

    RequiredOptional, with default
    QUESTION (AI_ASK); ROOM (AI_ANALYZE_ROOM, AI_SUGGEST_SCENE); NAME (AI_RECORD_EVENT); KEY, VALUE (AI_SET_CONTEXT); STATEMENT (AI_LEARN_PREFERENCE); OCCASION; TYPE and PERIOD (AI_GENERATE_REPORT — no defaults); exactly one of DEVICE / ROOM (AI_START_DIAGNOSTIC; DEVICE 0, Composer's empty selector, counts as none); TITLE, MESSAGE (AI_SEND_NOTIFICATION)CATEGORY → General (AI_RECORD_EVENT); AUDIENCE → Homeowner (AI_SEND_NOTIFICATION); ROOM (AI_ASK, AI_RECORD_EVENT, AI_LEARN_PREFERENCE) and DETAIL (AI_RECORD_EVENT) → none

    Text sent to the cloud

    The platform refuses the whole request (invalid_args) for one text field over its bound, or containing a character of its UNPRINTABLE set (U+0000–U+0008, U+000B–U+001F, U+007F–U+009F, U+2028, U+2029). So every text field is cleaned before it is sent (aicore.commands.sanitise): every C0 control (TAB and LF too), DEL, every C1 control, U+2028 and U+2029 becomes a space; a byte that is not well-formed UTF-8 is dropped; the ends are trimmed with the platform's whitespace set. Names Director supplies are then cut on a character boundary to the platform's bound — room_name 64, device_name 120 characters — and a name with nothing printable left is not sent. Typed text (QUESTION, STATEMENT, VALUE, OCCASION, TITLE, MESSAGE, NAME, DETAIL) is cleaned the same way and refused over its bound.

    The cloud body carries typed text whole; only the envelope's copy is bounded. Every payload string is cut to 512 bytes and every label to 120 bytes, between two UTF-8 characters, before the shared envelope sees it (the cut marks the envelope partial): an AI_ASK question of 500 three-byte characters is 1,500 bytes. The shared envelope library used by the other SmartBuildOS drivers still cuts at a byte and can split a character (KNOWN-ISSUES KI-1, open).

    AI_RECORD_EVENT is a marker, not learning

    AI_RECORD_EVENT (NAME ≤ 120, DETAIL ≤ 400, ROOM, CATEGORY) makes no cloud call: it records an ai_core.record envelope on the durable event path (severity warning for Security and Safety). It is a dealer's explicit marker (architect's ruling, 18 November 2026): it is recorded whether learning is off, on or paused, but it still honours the exclusions — refused for an excluded room (… is excluded by the AI Core configuration) or category (not recorded (excluded_category)). The cloud's learning engine never learns from it.

    AI_SET_CONTEXT

    The context key is sent as key in the set_context cloud body (the platform validates key) and as context_key in the ai_core.command envelope, because the envelope's credential rules redact a field named key. The platform keeps one value per system and key and answers completed at once.

    What happens after a cloud command

    Validate → new request_id (aic-<uuid>, written to AI_LAST_REQUEST_ID) → ai_core.command envelope (correlation id = request id) → cloud request with idempotency_key = request id → the Agent POSTs the platform route.     Events

    Event ids are permanent (programming binds by id). Events 1–8 and 10 are fired by the platform through deliver_result / raise_event; event 9 only by the driver itself.

    Wire the events you care about to the Notification Agent for push or email: a driver cannot send push or email itself.

    Variables

    Ids 4000–4010, order frozen. AI_LAST_CORRELATION_ID (4010) is an addition beyond the brief's ten: it holds the correlation_id of the last raise_event — for Approval Required, Action Completed and Action Failed, the platform's action id — so programming and support can tie the event to the action in System Studio. An event without one sets it to empty, so it never names an earlier event's subject. Sizes are in bytes: AI_LAST_RESPONSE ≤ 1024 (a longer result keeps its first ≤ 1021 bytes, cut between two UTF-8 characters, followed by ...), AI_LAST_EVENT_DETAIL ≤ 512, Last Error / AI_LAST_ERROR ≤ 240. LEARNING_ACTIVE is false until a valid configuration or set_learning switches learning on. All except AI_STATUS, AGENT_CONNECTED and LEARNING_ACTIVE (recomputed at start) are persisted and repainted after a reload. AI_STATUS shows starting until the first state is computed.

    Chapter 12

    Security

    The controller stays light and holds no secrets; the cloud authorizes every tool call with deterministic code; household activity is a second gate; and the homeowner keeps control of what is learned.

    Credential storage

    • Provider keys are customer-supplied and entered only in System Studio (Provider & settings). They are stored as secret-box ciphertext in ai_core_provider_credentials; the key field is write-only and every answer carries only provider, scope, ••••last4 and test status (the PUT answer is cache-control: no-store). Key changes are audited (credential.stored, credential.rotated, credential.store_refused, credential.deleted, credential.tested).
    • Keys never transit the controller. The driver refuses any configuration document containing a credential-shaped key or a display string that looks like a key.
    • The provider layer removes key material from every string that leaves it; connectivity tests return an error kind, never the vendor message.
    • The Agent's pairing token authenticates its cloud calls; module tokens never leave the controller.
    • No AI tool can read a secret: the credential risk class has no tool and is refused by the engine.
    • Calendar OAuth tokens are stored encrypted (ai_core_concierge_connections), the OAuth state as a hash with an encrypted PKCE verifier; no route ever returns a token.

    Permissions

    The permission engine (src/lib/ai-core/authz/engine.ts) is pure, synchronous and total: every input it does not recognise is a denial. Its inputs are built by the server from the session — actor, property permission mode, tool (risk, household flag, verb, feature), target (device type from the registry), controller capabilities, entitlement features, pre-approved rules, learning basis and the route gate's would-deny flag.

    Risk classExamplesRule
    readhistory, registry, usageallowed in every mode, subject to role and household gate
    lowlights, thermostat within bounds, scenesobserve: deny · recommend: approval · execute_low_risk: allow only on a matching pre-approved rule, else approval
    highlocks, garage, security, access controlobserve: deny · otherwise explicit homeowner approval per action; never on learned behaviour
    externalreservations, purchases, calendar writesobserve: deny · otherwise explicit homeowner confirmation; never for an automation or on learned behaviour

    Property isolation

    • Tenant and property come from the session or the Agent's pairing token only; the controller route never reads them from a frame body.
    • All AI Core tables (ai_core_*) carry a composite foreign key to the property, have row-level security on, and grant access only to the service role (revoke-first).
    • Device ids are validated against the property's registry; a homeowner can act only on their own client's properties; own-scope staff roles see only their clients' properties (anything else is 404).
    • Idempotency keys are unique; replays are refused; per-property rate limits live in the database.
    • Cross-property and cross-tenant isolation tests pass in simulation (7.5).

    Route gates

    Every staff route checks, in order: the platform permission (monitoring:view or manage); the audit-mode would-deny flag; a uuid property_id in the caller's company (another company's looks like no property: 404); a linked Control4 system; the SBOS_AI_CORE entitlement (403 not_entitled, 503 when unreadable). Families add the household grant (homecontrol:view), homecontrol:manage for action writes, the AI_LEARNING / AI_ACTIONS / AI_CONCIERGE feature, and for conversations a property visible to the caller's own session. Portal routes resolve the client portal session, the property (must belong to the caller's client), the system, and the licence only for the directions that need it: the homeowner's learning controls and every "safe direction" (decline, revoke, cancel, dismiss, disconnect) never need the licence.

    Four operations staff cannot send

    Through the staff route POST /api/monitoring/control4/commands, staff may send refresh_status and run_diagnostic to AI Core; deliver_result, raise_event, set_learning and apply_config are refused with 403. Each is produced only from a record the platform owns (a job's result, an action, the settings), so a hand-made copy cannot fake an answer, an approval event, or switch learning on over a homeowner's pause.

    Approval policies

    See Chapter 8. In short: low actions — the requester (or the homeowner for automations and learned behaviour), unless a consented rule covers them in execute_low_risk; high and external — the homeowner, per action; programming — a person in Composer Studio.

    Audit

    ai_core_audit_events is append-only (a trigger refuses UPDATE and DELETE except a foreign key nulling its pointer). The orchestrator writes turn.started, provider.call, budget.refused, turn.round_limit and answer.invalid; every tool call records its decision; credential changes are recorded (e.g. credential.deleted). The audit trail for every tool call and decision is Completed in simulation (7.7).

    Privacy controls and prompt-injection defence

    • Learning is off by default; household activity needs homecontrol:view in addition to the route gate; the homeowner can pause, exclude, correct, export and erase what was learned, and a pause reaches the controller and the cloud at once (Chapter 7).
    • No retention job exists for any ai_core_* table: rows stay until a route, a cascade or a company deletion removes them.
    • The system prompt is a static constant that contains no tenant data; telemetry reaches the model only inside tool results marked {"untrusted":true,"source":…,"data":…}.
    • The tool list is fixed before the first round and does not change because of anything a tool returns. A call the model was talked into by injected text is refused by the engine like any other. Prompt-injection tests with hostile device names, titles and calendar text pass in simulation (7.6).
    • A historical answer with no surviving evidence is replaced in full by I don't have evidence for that.
    • OpenAI calls use store:false.

    Extension guidelines

    1. Extend, do not fork. Use the module contract, command queue, Flight Recorder store, licensing, notifications, audit and secret box that exist.
    2. New tool: defineTool with a dotted lower-case id, a wire name matching ^[a-zA-Z0-9_-]{1,64}$, a declared risk (read, low, high, external, programming), a declared household flag, a closed object schema (additionalProperties: false), and — for any action tool — a resolveTarget that reads the target from the registry. There is no way to declare a credential risk.
    3. New cloud op or capability: add it to the Agent policy table and protocol.ts together; it is a driver release.
    4. New Composer event: append an id (ids are permanent) and add its key to raise_event's closed list on both sides.
    5. Evidence: any historical claim must cite event ids a tool returned in the same turn.
    6. Prove guards: a thing is tested only when a test that fails without it passes.
    7. Label simulations as simulations in code, UI, tests and docs.
